# 双模型接口验证

本地模拟测试用于验证网关实现。开启真实自动切换前，需要验证具体 Opus 和 Flash 接口对同一段历史的双向兼容性，随后用任务验收衡量质量。

## 接入顺序

1. 在本地 config.json 填写实际 URL、api_key、模型 ID、上下文限制和价格，运行 check。也可继续使用 api_key_env 从环境变量读取密钥。
2. 用 high 模式执行一个简短解释和一个读取文件的任务，检查 SSE、工具结果及数据库 usage。
3. 用 low 模式执行相同场景。核实响应中的模型标识、分离 token 计数、缓存字段与供应商账单口径。
4. 用 shadow 模式收集实际工作任务的决策分布和分类额外费用。shadow 本身不能证明 Flash 能完成任务。
5. 使用独立测试会话和普通文本历史，开启 auto 及 allow_text_switch，验证两个方向的切换。
6. 同一会话先用 Flash 生成 thinking 历史，再提问“分析并发架构和死锁路径”。auto 应命中 complexity_rule 并调用 high，显示 complexity_overrides_thinking，不额外调用分类器。核对高档接口能否接受原始 thinking 与工具记录；若上游拒绝，应看到原始错误且没有自动降级或重试。本地模拟测试只证明路由与透传行为，不能证明真实供应商的签名兼容性。

## 必验场景

| 场景 | 验收依据 |
| --- | --- |
| 两个方向的普通文本接续 | 无结构错误，前文约束和事实保留 |
| 客户端工具调用接续 | tool_use_id 与 tool_result 对应，执行结果一致 |
| 复杂任务 / 高级内容的 thinking 历史 | auto 命中 complexity_rule / content_requires_high_capability 时选 high，原始内容保留，上游兼容性另验 |
| 服务端状态与内容能力冲突 | auto 来源 Flash 被服务端状态锁定且内容需要 high 时返回 409，禁止派发到能力不符的 Flash |
| 普通任务的 thinking / 服务端状态历史 | 保留来源；未知来源明确报错，未静默剥离 |
| 上下文压缩 | 使用所属主代理的来源状态，压缩后重新评估 |
| 中断及重试 | 中断费用标未知，客户端重试单独记账，无拼接输出 |
| 主代理与并行子代理 | 各自来源和缓存状态独立 |
| 缓存写入及读取 | usage 与供应商解释一致，预测和实际可区分 |
| 服务端模型别名变化 | 不把其他模型按原价格错误核算 |

## 质量与成本对照

选择有明确验收标准的代表性任务，固定代码快照和测试环境，在隔离目录分别运行固定 Opus、固定 Flash 和自动策略。每个策略包含全部推理、分类、重试、返工及评估费用。保持缓存预热条件可比并重复采样，报告样本量、未评估数量和结果波动。

先约定可接受的质量差距，再比较每个成功任务的成本和耗时。单步输出评分只作为辅助证据。当前版本没有自动执行这套实验；这份流程用于后续联调和评估阶段。
